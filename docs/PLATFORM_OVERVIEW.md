# Minfy Resolve Platform Overview

## What this tool does

Minfy Resolve is an internal technical knowledge and expert-discovery platform. It helps employees record technical problems they have already solved, then helps other employees find those verified solutions later when they hit a similar blocker.

The platform is designed for technical incident reuse, not general chat. A user can search with a natural-language description, an exact error message, a technology name, or a deployment context. The system returns matching historical solutions, the documented root cause, the resolution steps, verification status, and the approved work contact for the employee who solved it.

## Core problem it solves

Engineering teams repeatedly solve similar issues across projects, environments, and customers. Without a searchable internal knowledge system, that knowledge stays scattered in ticket comments, chat messages, individual memory, and private notes.

This creates several recurring problems:

- engineers spend time rediscovering fixes that already exist;
- teams depend on knowing the right person instead of finding the right evidence;
- exact error messages are hard to search across informal channels;
- AI-only answers can invent details if they are not grounded in verified internal records;
- employee ownership, contact details, permissions, and verification status must remain controlled by company data, not generated by a model.

Minfy Resolve addresses this by combining a structured solution repository, hybrid retrieval, access control, and grounded summaries.

## What it is made of

The review build is built as a monorepo with these main parts:

| Layer | Main technology | Purpose |
|---|---|---|
| Web application | React, TypeScript, Vite | Employee-facing product interface |
| API | FastAPI, Pydantic | Authentication, repository workflows, search, review, profile APIs |
| Data access | SQLAlchemy, Alembic | Database models, migrations, transactional access |
| Database | PostgreSQL with pgvector | Structured records, full-text search, vector search |
| AI adapters | Configurable NVIDIA or Amazon Bedrock adapters | Embeddings and grounded summaries |
| Local runtime | Docker Compose | Runs PostgreSQL, API, and web locally |

The frontend is a first-class product surface for the core workflows. The important platform value still sits in the repository model, authorization rules, retrieval pipeline, review workflow, and grounded answer generation, but leadership and hackathon judges experience that value through the search flow, ledger-style result rows, citations, review states, and solver profile handoff.

## Main features

### 1. Structured technical solution repository

Employees can record a solved problem with:

- problem title;
- technical environment;
- symptoms;
- exact error message;
- root cause;
- resolution steps;
- code or command evidence;
- technologies involved;
- visibility level;
- ownership metadata.

Drafts can be saved before they are complete. A solution only becomes trusted search knowledge after it is submitted and reviewed.

### 2. Reviewer verification workflow

Reviewer users can inspect submitted solutions and decide whether to:

- approve the solution;
- request changes;
- reject the solution.

Verified solutions become eligible for trusted retrieval. The platform stores reviewer decisions, timestamps, reviewer identity, and review notes so the search result has a clear trust trail.

### 3. Expert discovery

Every solution is connected to the employee who solved it. Search results show structured solver details from PostgreSQL, including:

- display name;
- job title;
- team;
- department;
- approved contact email or handle;
- skills;
- visible verified contributions.

This data is not generated by AI. It always comes from structured database records.

### 4. Editable employee profiles

Signed-in users can maintain their own profile information:

- display name;
- job title;
- contact handle;
- bio;
- skills.

This supports expert discovery because searchers need to understand who owns the solution and when that person is relevant to contact.

### 5. Hybrid search

Search combines several retrieval signals:

- PostgreSQL full-text search for keyword and phrase relevance;
- exact-error matching for copied error messages;
- pgvector semantic similarity when embeddings are configured;
- technology filtering;
- verification status;
- authorization filtering;
- deterministic scoring and pagination.

This is stronger than simple keyword search because users often describe the same issue in different words. It is also safer than a generic chatbot because all results must map back to real solution records.

### 6. Grounded summaries

For reliable matches, the platform can generate a concise summary from the highest-ranked authorized records.

The generated summary is grounded because:

- only retrieved and authorized solution context is sent to the model;
- employee names, emails, job titles, ownership, permissions, and verification data are never generated by the model;
- returned citations must reference original solution records;
- malformed, uncited, or unsupported model output is rejected;
- no-answer searches do not invoke generation.

## Why RAG is needed

RAG means retrieval-augmented generation. In this platform, RAG is needed because the system must answer technical questions using internal verified knowledge, not generic model memory.

A plain language model is not enough for this use case because it can:

- produce a plausible but wrong fix;
- invent an expert who did not solve the issue;
- invent contact details or ownership;
- ignore internal visibility rules;
- miss company-specific environment details;
- cite no original record.

RAG solves this by separating responsibilities:

1. The database stores trusted facts: problems, solutions, owners, reviewers, permissions, and contact information.
2. The retrieval system finds relevant authorized records.
3. The model summarizes only the permitted technical context.
4. The API validates the generated answer and returns citations.

This gives the user a helpful explanation while preserving traceability and access control.

## Retrieval pipeline

The approved retrieval flow is:

1. Authenticate the employee.
2. Accept the search query.
3. Extract optional metadata filters.
4. Create the query embedding when an embedding provider is configured.
5. Run pgvector similarity search.
6. Run PostgreSQL full-text search.
7. Match exact error-message fragments.
8. Apply visibility and authorization filters.
9. Merge duplicate candidates by solution ID.
10. Rank results using deterministic scoring.
11. Apply the no-answer threshold.
12. Retrieve employee and ownership data from PostgreSQL.
13. Send only permitted technical solution context to the generation model.
14. Generate a grounded summary when requested.
15. Return citations to original solution records.

## What AI is allowed to do

AI may:

- create embeddings for solution documents and search queries;
- help find semantically similar records;
- summarize retrieved technical solution context;
- explain matching results using citations.

AI must not generate:

- employee names;
- employee emails;
- job titles;
- teams;
- departments;
- contact details;
- solution ownership;
- verification status;
- access permissions.

Those fields always come from PostgreSQL.

## Security and governance controls

The MVP includes these controls:

- JWT authentication;
- role-based authorization;
- object-level authorization;
- password hashing;
- parameterized database access through SQLAlchemy;
- restricted CORS;
- upload size and file-type limits;
- secret detection before submission and packaging;
- audit logging;
- permission filtering before any model call;
- no personal contact data in embeddings;
- no source-controlled AWS credentials.

## Current review build status

The current review build is implemented and runnable with Docker Compose. It includes:

- authentication;
- searchable verified solution records;
- exact-error and keyword search;
- semantic retrieval when embeddings are configured;
- grounded summary generation when a generation provider is configured;
- solution authoring;
- draft persistence;
- reviewer approval workflow;
- employee profile and profile editing;
- expert discovery;
- safe source packaging;
- repository secret scanning;
- an expanded synthetic showcase corpus.

The current showcase seed generates:

- 43 employee profiles;
- 679 generated technical solution records;
- 567 generated verified solution records from the current seed run.

The local database may contain a higher total count if older local records were preserved instead of resetting the database.

## Known limits

The current version is a local review build. These items are not fully productionized:

- company SSO is not included;
- malware scanning for uploaded files is represented but not connected to an external scanner;
- production deployment automation is outside the current local scope;
- real employee data should replace the seeded showcase profiles before live internal use;
- the synthetic solution corpus is for demonstration and evaluation, not production runbook authority.

## Recommended next additions

The most valuable next improvements are:

1. Connect real company identity data or SSO.
2. Import approved real solution/runbook data.
3. Configure the approved production embedding and generation provider.
4. Add an ingestion workflow for existing documents or tickets.
5. Add reviewer assignment rules.
6. Add stronger analytics for no-answer searches and repeated blockers.
7. Add production backup and restore procedures for PostgreSQL.
